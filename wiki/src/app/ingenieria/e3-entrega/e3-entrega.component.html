El gate es proporcional al corte

Ningún ciclo se cierra sin evidencia ejecutable, y la verificación que se corre depende de lo que el corte toca. Un spike no corre el gate completo; un corte vertical sí.

Corte Comandos
Siempre typecheck · lint · format:check
Backend test:api
Backend con base o con dev branch test:api:db · test:api:db:branch
Frontend test:web:⟨FE⟩
Frontend o shared tocado build:web:⟨FE⟩
Build del backend build
Arnés e2e tocado typecheck:e2e
Ruta crítica test:e2e · test:e2e:branch

Reglas de corrida: un comando por invocación, una sola corrida de verificación a la vez y nunca npm test encadenado. npm test es unitario; el arnés levanta backend y frontends.

Evidencia: .roo/rules/04-verificacion.md; README.md §6.

Contrato de scripts

Todo se ejecuta desde la raíz y hay un solo lockfile. Cada build de frontend compila shared antes, porque el frontend resuelve sus tipos desde shared/dist; el despliegue invoca los scripts de la raíz y nunca la variante por workspace.

  • build + start: producción ejecuta node backend/dist/index.js, nunca tsx ni --env-file.
  • El build de un frontend ejecuta brand:index después de ng build: la marca entra al artefacto, no al fuente.
  • invite es el único script de administración: reenvía sus banderas al workspace del backend, por eso se invoca con -- antes de los argumentos.

Evidencia: package.json de la raíz; commits 769ba25 y b13d03f (2026-10-25 y 2026-10-31).

Bases: cuatro locales, dos remotas

Objetivo Base Comando
main mudanzapp db:migrate · db:ping
test mudanzapp_test db:migrate:test · db:ping:test
branch mudanzapp_branch db:migrate:branch · db:ping:branch
branch-test mudanzapp_branch_test db:migrate:branch:test · db:ping:branch:test
remoto main Neon, cadena directa db:migrate:remote · db:ping:remote
remoto branch Neon, cadena directa db:migrate:remote:branch · db:ping:remote:branch

La URL de pruebas y las de la dev branch se derivan de la de desarrollo con los sufijos _test, _branch y _branch_test: no se escriben a mano, no se transportan y nunca se imprimen. La derivación es el único camino autorizado.

Las migraciones se aplican a mano, nunca en el arranque. El runner ejecuta todos los backend/sql/*.sql en cada invocación y cada archivo va en su propia transacción; un archivo con control de transacción propio se rechaza con migration-transaction-control. Las bases _test son local-only: un objetivo de prueba remoto se rechaza con error estable.

El arnés e2e no migra: exige db:migrate:test (o db:migrate:branch:test) corrido antes, y falla ruidosamente si el esquema falta.

Evidencia: README.md §3 y §7; .roo/rules/06-datos.md; commits f572f40 (2026-10-25) y b486329.

Arnés e2e

Playwright, fuera de los workspaces y con sus salidas junto al arnés. Un project por frontend con su ng serve en puerto explícito, un solo worker y una única base de pruebas compartida por las suites. El envoltorio deriva e inyecta la URL de pruebas dentro del proceso; un npx playwright test a mano se rechaza con e2e-wrapper-required en vez de apuntar a la base de desarrollo.

Las integraciones corren en modo fake: ninguna prueba depende del proveedor de identidad, del almacén ni del motor de IA.

Evidencia: e2e/playwright.config.ts, e2e/support/harness.ts; commit 2bb04f7 (2026-10-23).

Humo del backend

Ruta Respuesta
GET /health Siempre 200 con el estado del proceso y de la base: liveness no es readiness
GET /health/db 200 con la base en ok, o 503 con not-configured o error

El servidor no lanza al importar: lo que falta de configuración se registra y el humo sigue respondiendo. El orden de middleware es CORS, cuerpo JSON, humo, identidad y manejador de errores; el apagado cierra primero el servidor y después la base. Las tablas y los códigos de error son de A4.

Evidencia: README.md §8; commit 41a4d25 (2026-10-23).

Despliegue

Pieza Contrato
Backend Railway, contrato en el dashboard: build npm run build, start npm run start, healthcheck /health y watch paths. No hay railway.json ni railway.toml.
Puerto PORT=3000 como variable del servicio; el target port y el healthcheck la siguen y nunca la contradicen.
Frontends Tres Workers de assets —mudanzapp, mudanzapp-shop y mudanzapp-wiki—; el nombre del Worker es idéntico al name de su wrangler.jsonc.
Workers Builds Cada Worker conectado al repo en main, root directory /, build npm run build:web:⟨FE⟩, deploy npx wrangler deploy -c ⟨FE⟩/wrangler.jsonc y sin build watch paths.
Configuración environment.production.ts se compila: si cambia el host del backend hay que reconstruir ese Worker. APP_BASE_URL lleva todos los orígenes de los Workers.

Sin watch paths cada push construye los tres Workers; con patrones, un commit fuera de ellos no genera build ni check run y producción se queda en el artefacto anterior sin avisar. No hay workflows en el repo: el estado del despliegue se lee en los check runs del commit. El wrangler deploy manual es el respaldo de emergencia.

Evidencia: README.md §12; commits ed59071, 907854b y 704f7f5.
